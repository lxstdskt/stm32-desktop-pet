### 🕳️ 2. 走的弯路与思维纠偏
1. **备忘录误区（.txt vs .md）**：
   - *原想法*：想用 `.txt` 记事本或者腾讯文档随便记记引脚和说明。
   - *纠偏*：做硬件极其讲究引脚对齐，`.txt` 换台电脑排版就会乱，容易导致接错线烧片子。必须用 Markdown 锁死表格格式，且文档必须跟代码绑定在同一个 Git 仓库里，绝不能代码和说明书分家。
2. **急于求成误区（还没想好就想写代码）**：
   - *原想法*：觉得功能还没定，等定好了再建工程。
   - *纠偏*：正规军的做法是**“留出骨架，按需填空”**。哪怕外设还没买，也要先把工程文件夹建好，空表反向约束未来的采购和接线。
3. **工具叠加误区（以为 CMake 可以和 Keil 混用）**：
   - *原想法*：电脑里本来就有 Keil5，以为只要再下载个 CMake 配合着用就行。
   - *纠偏*：Keil5 自带了编译器和构建体系，而 CMake 的使命就是**替代** Keil 的构建体系。两者是互斥的，强行混用会导致系统崩溃。

### 📦 3. 今日核心收获（详细备忘）

#### ① 核心实操：Git 仓库的建立与提交 (烂熟于心的三板斧)
以后每次写完一段代码、改完文档或者调通一个硬件，只需要在终端执行：
```bash
git add .
git commit -m "说明内容（比如：feat: 调通OLED屏幕显示）"
git push

```

> *Tip：Git 就是我的“游戏存档点”，代码写崩了随时能回档。遇到终端报 `did not match any files` 时，直接用 `git add .`（一网打尽法）最稳妥。*

#### ② 架构认知：APP 与 BSP 到底是什么？

* **BSP (板级支持包)**：单片机的**四肢与五官**。只管底层寄存器和引脚。比如只负责“给电机发 PWM 波”，完全不管电机为什么要转。
* **APP (业务逻辑层)**：单片机的**大脑**。只做战略决策，不碰具体引脚。比如大脑决定“如果听到人说话，就命令电机转头”。
* *好处*：以后换电机型号，只改 BSP，APP 核心逻辑一行不用动。

#### ③ 编译工具链底层逻辑：“全包快餐店” vs “米其林后厨”

* **传统模式 (Keil5 = 快餐店)**：点一下 Build 就出固件，但过程完全黑盒，且被死死绑定在 Windows 系统上，无法做企业级 CI/CD 自动化编译。
* **工业界模式 (现代跨平台工具链 = 米其林后厨)**：
1. **CMake（餐厅经理）**：负责看懂我的 `CMakeLists.txt`，画出详细的工程构建图纸。
2. **Ninja（包工头/执行总监）**：拿着图纸，调度电脑 CPU 多核极速并发干活（编译速度秒杀 Keil）。
3. **arm-none-eabi-gcc（掌勺大厨）**：真正的编译器，负责把 C 语言翻译成 STM32 认识的机器码。



#### ④ Markdown 避坑指南：排版失效的隐形杀手

* **语法铁律**：标题 `#` 或列表项 `-` / `*` 后，**必须紧跟一个英文半角空格**；区块之间必须留**空行**；行首绝对不能有莫名其妙的空格缩进。
* **插入图片**：图片必须随工程走，保存在 `assets/` 文件夹下，使用相对路径：`![说明](assets/图片名.png)`
